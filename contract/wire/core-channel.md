# Core channel

While the server moves from Bun to Rust family by family (Rust migration
plan, section 8.2), two processes serve it together: the **front**, which
holds the port, TLS, auth and the browser WebSockets, and the **core**, a
portless process it spawns. In stage 1 the front is the Bun server and the
core is the Rust binary (`roamgate core`); in stage 2 (phase 7) the roles
swap and the same channel carries the Bun code as the core. This file is the
contract between them. The Bun side is `server/src/core-channel/`, the Rust
side the `roamgate-sidecar` crate; both are held to
`contract/vectors/core-channel.json`.

Nothing here runs unless the front is told where the core is: without
`ROAMGATE_CORE_BIN`, the Bun server opens no socket, spawns nothing, watches
no file and behaves exactly as before.

## Variables

| Variable                   | Read by | Meaning                                                                                                                                                                                                                              |
| -------------------------- | ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `ROAMGATE_CORE_BIN`        | front   | Path of the Rust `roamgate` binary to run as the core (`<bin> core`). Unset or empty: no core, nothing below happens.                                                                                                                |
| `ROAMGATE_CORE_CHANNEL`    | core    | Where to connect: a Unix socket path, or a named pipe (`\\.\pipe\...`) on Windows. Set by the front for its child only.                                                                                                              |
| `ROAMGATE_CORE_TOKEN`      | core    | 64 hex digits the core proves itself with in `hello`. Set by the front for its child only.                                                                                                                                           |
| `ROAMGATE_CORE_SERVED_LOG` | core    | A debug core appends `<family> <what>` to this file for each browser call, HTTP request and CLI command of a family it served: the parity suite's proof that a family it gave to Rust was served by Rust. A release core ignores it. |
| `ROAMGATE_CLI_EXEC`        | core    | The front's executable, which `update` and `rollback` replace: set by the Bun CLI when it passes a command through (see CLI pass-through), and by the Bun server for the core it spawns. Unset: the core's own.                      |
| `ROAMGATE_CLI_VERSION`     | core    | Set with `ROAMGATE_CLI_EXEC`: that executable's version.                                                                                                                                                                             |
| `ROAMGATE_CLI_STANDALONE`  | core    | Set with `ROAMGATE_CLI_EXEC`: `1` when that executable is the standalone binary, `0` when it runs from source.                                                                                                                       |
| `ROAMGATE_CORE_TEST`       | both    | `1` turns on the `test.echo` family and reverse target used by the channel's own cross-language test. Honoured only by a server run from source and a debug build of the core; a release ignores it.                                 |

The core gets the front's environment otherwise (HOME, data root, record
mode), minus the test clock's variables, which the front has already removed
from its own environment: the core runs on the real clock.

## Process

- The front creates `<data>/runtime` (0700), listens, then spawns the core
  with `ROAMGATE_CORE_CHANNEL` and `ROAMGATE_CORE_TOKEN`. The spawner always
  listens and the child always connects, so neither waits on the other's
  readiness: the socket exists before the child starts.
- The socket is `<data>/runtime/core-<front pid>.sock`. When that path is
  longer than 100 bytes (Unix socket paths are limited to 104 to 108), it is
  `core.sock` in a fresh 0700 directory made with `mkdtemp` under the
  temporary directory. On Windows it is the named pipe
  `\\.\pipe\roamgate-core-<front pid>-<16 random hex digits>`. Stale
  `core-<pid>.sock` files of processes that no longer run are removed at
  start; the front removes its own when it stops.
- Startup does not wait for the core: the port opens and `/healthz` answers
  as before, and every family stays with the front until the core says
  `hello`.
- The core's stdout and stderr are the front's (its log lines land in the
  same journal), its stdin is closed.
- A core that does not say `hello` within 10 s, or goes 30 s without
  sending a frame while a ping has waited 20 s for its `pong`, is killed
  (after a stalled event loop the front pings first and waits those 20 s). A core that exits or is killed is spawned
  again after 1 s, doubling up to 5 minutes, and the delay starts again at
  1 s once a core has stayed up 10 minutes. A `refused` core (wrong token or
  protocol) waits the same way, so a stale binary never spins.
- The core exits when the channel closes (the front stopped or died): it
  never outlives its front.
- The front stops the core with `bye`, closes the channel, and kills it if it
  still runs 3 s later.
- Fail safe: while there is no core (none configured, not started yet,
  crashed, refused, being restarted), every family is served by the front,
  whatever the owners table says. In stage 1 Bun still has every family's
  code, so a crash of the core costs nothing but the time Rust was the
  owner.

## Frames

The voice helper's codec (`contract/vectors/voice-frames.json`): a
little-endian u32 length of what follows, a kind byte, the payload. The
channel accepts frames up to 64 MiB (length field, kind byte included).

| Kind | Payload                                                                                                                                                              |
| ---- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 0    | One message: a compact JSON object, UTF-8                                                                                                                            |
| 2    | A body chunk: the stream's u32 (little-endian), a flags byte, then the bytes. Flags: bit 0 `END` (last chunk), bit 1 `RESPONSE` (a response's body, not a request's) |

Other kinds are an error that closes the channel. Body chunks carry at most
256 KiB of bytes each.

## Messages

Every message has `t`, its type. Requests (`call`, `reverse_call`, `http`)
carry an `id`: each side numbers its own requests from 1, and a `reply`,
`http_resp`, `cancel` or `ack` names the id of the request it is about, in
the numbering of the side that sent that request. A message of an unknown
`t` is ignored (logged once), so either side can add messages without the
other breaking.

| `t`            | From                | Fields                                                                                                                               | Meaning                                                                                                                                                                                                                                                                                |
| -------------- | ------------------- | ------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `hello`        | core, first         | `protocol` (1), `token`, `side` (`rust` or `bun`), `version`, `pid`, `families` (the families it implements), `test` (bool)          | The core introduces itself.                                                                                                                                                                                                                                                            |
| `welcome`      | front               | `protocol`, `side`, `owners`, `shadow`, `clock` (optional)                                                                           | The token and protocol are right; `owners` and `shadow` as in `owner`. `clock`: the front runs on the test clock (contract/wire/test-clock.md), whose time this is; see Families in the core.                                                                                          |
| `refused`      | front               | `reason`                                                                                                                             | Wrong token or protocol; the front closes the channel.                                                                                                                                                                                                                                 |
| `owner`        | front               | `owners` (`{family: "rust" \| "bun"}`), `shadow` (`{enabled, rate}`)                                                                 | The owners table changed.                                                                                                                                                                                                                                                              |
| `call`         | front               | `id`, `method`, `params`, `ctx`, `shadow` (bool, optional)                                                                           | A browser RPC the core answers. `shadow: true`: a shadow read, whose answer is only compared.                                                                                                                                                                                          |
| `reply`        | either              | `id`, then `result` or `error` (`{message, code?, data?}`)                                                                           | The answer to a `call` or `reverse_call`, or an `http` that failed before its `http_resp`.                                                                                                                                                                                             |
| `cancel`       | the requester       | `id`                                                                                                                                 | The browser socket or HTTP client is gone: the answer is no longer wanted. The other side may stop; it still sends nothing or a `reply` it already had.                                                                                                                                |
| `push`         | core                | `message`, `key` (optional), `connection_id` and `connection_generation` (optional), `socket_id` (optional), `session_id` (optional) | A push to browsers: `message` is the browser message. With `connection_id` the front sends it in that connection's envelope; `socket_id` limits it to one browser socket, `session_id` to one login's sockets. `key` is its coalescing key, on the channel and on each browser socket. |
| `http`         | front               | `id`, `method`, `url` (path and query), `headers` (`[[name, value]]`, names lowercase), `ctx`, `body` (bool)                         | An HTTP request the core serves; with `body`, chunks of stream `id` follow, the last with `END`.                                                                                                                                                                                       |
| `http_resp`    | core                | `id`, `status`, `headers`, `body` (bool)                                                                                             | Its response head; with `body`, chunks with `RESPONSE` follow, the last with `RESPONSE` and `END`.                                                                                                                                                                                     |
| `ack`          | the body's receiver | `id`, `response` (bool), `bytes`                                                                                                     | That many more bytes of the body were consumed.                                                                                                                                                                                                                                        |
| `reverse_call` | core                | `id`, `target`, `args`, `ctx` (optional)                                                                                             | A call into what the front still owns. Answered by `reply`.                                                                                                                                                                                                                            |
| `ping`, `pong` | either              | `n`                                                                                                                                  | Liveness: each side pings after 10 s without sending anything, and the other answers at once, so a core waiting on a long call still sends a frame at least every 10 s while the front keeps sending (and so never pings).                                                             |
| `bye`          | either              |                                                                                                                                      | The sender is stopping; the channel closes after it.                                                                                                                                                                                                                                   |

`ctx` is what the front knows of the request: `connection_id`,
`connection_generation`, `socket_id` (the front's number for the browser
socket), `lane`, `session_id` (the first 16 hex digits of the SHA-256 of
the login's session token, never the token itself), and for HTTP
`client_ip`. Fields that do not apply are left out.

A body's sender keeps at most 4 MiB of it unacknowledged; the receiver
acknowledges bytes as its consumer takes them, so a slow browser slows the
core rather than filling the front's memory.

The front never forwards a WebSocket upgrade: in stage 1 it terminates every
browser WebSocket itself and the core reaches browsers through `push`.

In stage 2 the front (Rust) still terminates every browser WebSocket, and a
socket whose route the core serves (the Bun core: `/ws`,
`/api/notifications/ws`, `/api/voice/ws`, `/api/voice/call/signalling`, the
terminal sockets) becomes a **virtual socket** in the core, driven by the
messages of "Stage 2: the Rust front" below. The voice family's two sockets
go to the Rust core instead while it owns the family, on its own link to the
front ("The Rust core's link to the Rust front" below).

## Stage 2: the Rust front

From phase 7 the Rust binary can be the front (`roamgate front`, hidden; the
default stays the Bun front until the switch) and the Bun server its core,
on this same channel: the front listens and spawns, the core connects and
says `hello` with `side: "bun"`, every message above keeps its meaning.

| Variable                | Read by    | Meaning                                                                                                                                                                                                                                                                                                                                                                           |
| ----------------------- | ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ROAMGATE_SIDECAR_BIN`  | Rust front | The Bun server to run as the core: an executable (the Bun `roamgate`), or a `.ts` file run with `bun`. Its arguments are the front's server flags. Unset or empty: no Bun, the front runs its own executable as the standalone core (The standalone core below).                                                                                                                  |
| `ROAMGATE_CORE_CHANNEL` | Bun core   | As above. Set: the Bun server opens no port; it connects, says `hello` and serves what the front forwards. Its CLI is unchanged. With `ROAMGATE_CORE_BIN` (passed on by the front) it runs the Rust core as in stage 1: the owners table gives it its families, handed over as above; the front sets `ROAMGATE_CLI_EXEC` to its own executable, which the update family replaces. |

What the Rust front serves itself: `/health` and `/healthz`, the URL-token
login, `/login`, `POST /api/login`, `POST /api/login/pin`, `/api/logout`
(closing the browser sockets of that login with 4001 `Logged out`), the
login icon, the auth gate, the web app's files and manifest (a `GET` or
`HEAD` outside `/api/`, `/ws` and `/rendered/`, not cross-site), and the
`/ws` transport (flow control, coalescing, compression, chunking, the
acknowledgements, which never reach the core). Everything else is an `http`
to the core with the request as the browser sent it (cookie included) and
`ctx.client_ip`; the core runs its own routing on it, gate included, so a
route keeps its checks whichever side answers.

| `t`          | From  | Fields                                                                              | Meaning                                                                                                                                                                                                                                                              |
| ------------ | ----- | ----------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ws_open`    | front | `id`, `socket_id`, `method`, `url`, `headers`, `ctx`                                | A browser asks to upgrade: the core runs its routing on the request. Answered by `reply`: `result` `{accepted: true, transport: "ws" \| "raw"}` (the core upgraded it), or `{accepted: false, status, headers, body}` (the response the browser gets, body as text). |
| `ws_message` | front | `socket_id`, `data` (text), `binary` (bool, `data` base64)                          | A message of an accepted socket (`/ws` acknowledgements excluded).                                                                                                                                                                                                   |
| `ws_close`   | front | `socket_id`, `code`, `reason`                                                       | The browser socket closed; the core runs its close handling once.                                                                                                                                                                                                    |
| `ws_send`    | core  | `socket_id`, `data` (text), `binary` (bool), `context` (optional), `key` (optional) | A message to the browser. On a `ws` socket it goes through the front's flow with `context` and `key` as Bun's `sendWebSocketMessage` takes them; on a `raw` socket it is sent as it is.                                                                              |
| `ws_drop`    | core  | `socket_id`, `key`                                                                  | Forget a held message of that key (`dropCoalescedMessage`).                                                                                                                                                                                                          |
| `ws_end`     | core  | `socket_id`, `code` (optional), `reason` (optional)                                 | The core closes the browser socket.                                                                                                                                                                                                                                  |

`socket_id` is the front's number for the browser socket, as in `ctx`. A
`ws_send` before the `reply` to `ws_open` is held by the front until the
handshake is done. The core's virtual socket reports `readyState` 1 until
`ws_close` or its own `ws_end`, and a buffered amount of 0: back pressure,
the 8 and 64 MiB limits and the 30 s stall rule are the front's.

### The Rust core's link to the Rust front

The Rust core the Bun core runs also links to the Rust front, for the
browser sockets of the families it owns: the front listens on a second
channel and gives its Bun core the link's address and token, which the Bun
core's environment passes on to the Rust core it spawns.

| Variable                 | Read by   | Meaning                                                                                                    |
| ------------------------ | --------- | ---------------------------------------------------------------------------------------------------------- |
| `ROAMGATE_FRONT_CHANNEL` | Rust core | The link: `<data>/runtime/front-<pid>.sock` (the front's pid), set by the Rust front on its Bun core.      |
| `ROAMGATE_FRONT_TOKEN`   | Rust core | 64 hex digits the Rust core proves itself with in the link's `hello`, made once by the front at its start. |

Before its `hello` to the Bun core, the Rust core connects to the link and
says `hello` (`side: "rust"`, its families) with that token, so the link is
up by the time the Bun core routes it a family; the front's `ws_open` waits
on the link until the core heard the Bun core's `welcome`. The front answers
`welcome` (its owners table is the Bun core's, never the link's) or
`refused`, as on the channel. The front keeps the newest link: one that goes
closes the sockets it served with 1012 `Service Restart`, as the Bun core's
going closes all of them. Pings and liveness are the channel's (the Rust
core pings after 10 s of silence, the front drops a link silent 30 s). No
link (a Bun front, no `ROAMGATE_CORE_BIN`, a core that cannot reach it):
every socket is the Bun core's, as before.

For `/api/voice/ws` and `/api/voice/call/signalling`, the voice family's
paths, the front sends `ws_open` on the link first, the auth gate passed as
for any socket. The Rust core answers it while it owns the family (as told
by the Bun core's `owner`), with the family's own routing: accepted
(`transport: "raw"`), or refused with the response the browser gets (a
signalling that is not the call owner's, or from another site: 403
`forbidden`, as Bun's). While it does not own the family it answers
`{accepted: false, pass: true}`, and the front sends the `ws_open` to the
Bun core as for every other socket. The socket's `ws_message` and
`ws_close` then go on the link, and the core's `ws_send` and `ws_end` come
back on it; the messages and their meaning are the table's above.

### The standalone core

Without `ROAMGATE_SIDECAR_BIN` the Rust front runs no Bun: it spawns its
own executable as `roamgate core`, on this channel, as the spawner it is
for a Bun core (supervision, `bye`, the test clock relay), and sets
`ROAMGATE_CORE_STANDALONE=1` on it (`0` on a Bun core, so a Rust core the
Bun core runs never takes it from the front's environment).

| Variable                   | Read by   | Meaning                                                                                                                                                       |
| -------------------------- | --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ROAMGATE_CORE_STANDALONE` | Rust core | `1`: the core is a Rust front's own, with no Bun anywhere; anything else: a core beside or behind the Bun server, as above. Set by the Rust front on its core. |

- The front's `welcome` gives the core every family of
  `owners/families.json` (no owners table is read or written), with
  `clock` when the front runs on a test clock; each `advance` of the
  front's clock is then relayed as `internal.clock.advance` (no
  `ROAMGATE_TEST_CLOCK` of its own: the front sets it empty). There is no
  link (`ROAMGATE_FRONT_CHANNEL` is not set): every browser socket and
  every route the front does not serve itself go to the core on the
  channel, `ws_open` included.
- Before any browser request reaches it, the front calls
  `internal.front.start` with the server's configuration (`socket_path`,
  `client_socket_path`, `ssh_host`, `session`, `has_explicit_socket_path`,
  `has_explicit_client_socket_path`, `task_notification_source`,
  `auth_required`, `tls`: whether the front serves HTTPS, the scheme of the
  URLs it was reached on, `generations`); the core starts its connections from it
  (the host family's `internal.host.start`) and answers at once. At its
  shutdown the front calls `internal.front.stop` (the connections stop,
  at most 10 s) before `bye`.
- The core's `front` family takes what no family declares: the `/ws`
  socket (Bun's routing: the hello and the forwards registry on open, each
  RPC checked, routed to its connection and then to the family that
  declares its method, replies in the connection's envelope,
  `bridge.ping`, `bridge.status`, `bridge.pause_others`, and a
  connection's other methods passed through to its Herdr, topology lists
  as deltas), `/api/health`, and the connection-scoped routes
  (`/api/connections/<id>/...` and their legacy paths: `herdr-info` from
  the connection's Herdr, the file and agent-session routes from their
  families at their legacy paths, the connection in `ctx`; the uploads,
  staged per connection generation and swept while it runs), and the
  notification feed's socket `/api/notifications/ws` (its links on the
  origin the client reached, a ping answered at once by the front's link as
  it was for Bun's feed behind it). The browser RPCs Bun answered with its
  own code are answered with what Bun added over Herdr (overlays, agent
  activity and seen marks, worktree parents, git status, integration
  versions, `connections.agent_sessions` as changes from the version the
  socket holds, the agent profiles' settings). A method Bun answered with
  its own code that the core does not serve yet (the terminal bridge's
  `terminal.*`, creation from a browser terminal) fails with code
  `standalone_unported`.
  A connection's endpoints that a family declares (`agent_sessions`'
  downloads, `workspace`'s file routes) reach the `front` family first
  when their `ctx` names no connection: it resolves the connection and
  hands them to the family with it, as Bun routed them in place.
- Reverse targets are answered in the core's own process, from a registry
  the binary fills; a target nobody registered fails with code
  `unknown_target`, its message naming it. A debug core notes each such
  failure in `ROAMGATE_CORE_SERVED_LOG` as `reverse-missing <target>`, and
  each refused method or route as `unported <what>`. The core answers each
  with what Bun did for it, on its own families where Bun's went back into
  the core: the connections' (`connections.list`, `.ready`, `herdr.call`,
  `herdr.ping`, `herdr.setupGuard`, `host.run`, `workspace.ssh_run`,
  `activity.hostScript`, `agent_sessions.*`, `agent.transcript_tail`,
  `agents.addresses`; commands on an SSH host through the host family's
  session slots), conversation mode's and the Claude mods'
  (`conversation.host`, `.owned_panes`, `.prompt`, `claude_mod.*`; the
  Claude mod hub runs in the core from its start), `profiles.*`,
  `assistant.*` (a dispatch gate is the core's own closure, evaluated by
  its token), `settings.changed` and `settings.limit_resume.get`,
  `history.*`, `activity.dayInput`, `workspace.kept_steps`, and each
  generation's `host.runtime_start`, `.runtime_stop`, `.events`, `.status`
  and `.master_ready`, which feed the other families what Bun's runtime
  fed them (the workspace family's runtime and its events, conversation
  mode's `attach`, closed panes and sweeps, the activity log's signals,
  the usage limit resumer's pokes, the notifications a pane's events
  withdraw, Ranger's connection table, the claude start hook, and the
  review family's agents: `internal.review.agents` with this machine's
  socket key, on each status change and every second when changed).
  `server.scheduleExit` goes on to the front as the reverse call it is:
  the Rust front answers `{scheduled: true}` and a second later stops as
  on a signal, with code 0.
  The review family's targets are answered there too: `review.socket`
  (the agent socket's host: the connections' checkouts and Last steps, the
  boards' tools, notifications, the agent messenger, conversation mode's
  holder, prepared launches, the Claude mod hub), `review.host` (git reads
  of a checkout on its host, a merge request's from its forge when the
  checkout lacks its commits, agent panes and sessions), `review.forge`,
  `review.connection` (with the rendered pages' tokens and their sites'
  storage), `review.published` and `review.addThread`; the mr_reviews
  family's (`mr_reviews.connections` through `.agent_command`: the inbox's
  forge reads with this machine's glab and gh through the server's one
  forge gate, the reviews agent's turns on Claude Code), the work
  family's (`work.*`), the voice family's (`voice.errand_*`,
  `voice.work_*`), and the notification feed's (`notifications.feed`,
  `.clients` and `.current` with no feed socket held, `.clear_pane`);
  `mr_cache.load` has no reader to answer (the core's own readers read
  the cache in its process). `voice.session_cookie` goes on to the front,
  which answers `{cookie}`: a new login of its authentication, null when
  none is required.
- The `front` family also serves rendered reviews' pages,
  `/rendered/<token>/...` (the front sends them before its gate), and a
  sandboxed frame's request off its token (cross-site: a page saying so
  to a frame, 404 to anything else from an opaque origin), as Bun did.
- Pushes go to the `/ws` sockets the core holds, as `ws_send` with
  context `core-push` and the push's key, filtered and enveloped as the Bun
  front delivers them.

### Reverse targets

The front answers these in stage 1; a family that needs more adds one here.
The limit_resume family (Phase 2) added `connections.ready` through
`agent.transcript_tail` and `herdr.call`'s `timeout_ms`: what it needs of
the connections, conversation mode, the Claude mods, agent sessions and
settings.json, which Bun owns until their own phases. The work family
(Phase 4) added `work.review` through `history.work_changed`: the review
service, notifications, git and files on a connection, Herdr's panes and
workspaces, the agent sessions and the local history, each through Bun's
own code for the board. The mr_reviews family (Phase 8) added
`mr_reviews.connections` through `mr_reviews.agent_command`: the reviews'
connections, forge reads, settings.json writes, review service, Workspaces
tree, worktrees, model runs and agent profiles, through the same code Bun's
own reviews module uses (`mrReviewsHost`). The history family added
`history.release` (Bun's local history stops before the core's starts) and
`history.configure` (its route's settings change while Bun owns
settings.json).

### Pushes and coalescing

Each side writes its messages through one outbound queue. A push with a
`key` replaces a push with the same key that is still queued (not yet
written): the older one is dropped and the newer one goes to the end of the
queue, so it never overtakes messages queued before it. A push already
written is never replaced. The front also passes the key to each browser
socket's send, which coalesces the same way there.

## Families in the core

The core serves the families its binary implements (`hello.families`); a
browser call goes to the family whose `rpc` entries name its method, an
HTTP request to the one whose `http` entries name its path. A family's
code runs its background work (timers, watchers) and writes its files only
while the core owns it: the core tells each family when it starts owning
it (from `welcome` and each `owner`) and when it stops (an `owner` giving
it back, or the channel closing).

The front's own calls to a family are `call`s of `internal.<family>.<op>`
(no family declares the `internal.` prefix, so a browser never reaches
one): what the front still owns tells a Rust-owned family something
happened (a Herdr event, a setting changed). Each family documents its
internal calls and its reverse targets with its code.

### The history family

While the core owns the history family it runs the local history
(roamgate-history): the repo at `<data>/history` (or Settings'
`history.location`), its dirty sets and debounce (30 s after the last
change, 5 min at most), the 30 s polls of the file-backed areas, the start
pass a minute after it starts, a commit per Work change, `/api/history`
and `roamgate history`. The repo has one writer at a time: when the core
takes the family it asks `history.release` and starts its runtime once
Bun's has stopped, its last pass written; the front asks
`internal.history.release` before Bun's runs again (and before it stops the
core, so the core's last changes are committed). A pass of either side
also takes the repo's lock (`.git/roamgate-pass.lock`), as
`roamgate history commit` does, so a pass still running past a handover
makes the other wait and retry. The stores Bun still owns tell the core
their writes (`internal.history.changed`, `internal.history.work_changed`),
one at a time, in order; the core's Work board tells its history directly.
The files and commits are Bun's, byte for byte.

### The settings family

While the core owns the settings family it is settings.json's one writer
and the front a client of it. The front reads `internal.settings.get` once
(then keeps it), and makes each of its own changes on the settings of the
revision it holds, sent with `internal.settings.update` against that
revision; refused as `stale`, it reads again and makes the change again (5
attempts). Revisions start at the core's start time in milliseconds and
grow by one per write, so a restarted core never reuses one. The front
keeps what its write is answered; a write of the core's own handlers is
told to it with `settings.changed` before their answer goes out, and kept
when newer than its copy. When the core does not answer a read, the front reads
the file (the writer always replaces it whole). The core makes its store
afresh each time it starts owning the family and while Bun owns it reads
the file and writes nothing. The settings methods that also need Herdr,
git, worktree hooks, secret files or a provider are not the family's (its
`rpc` list names the others): their handlers stay in Bun and write through
the same writer.

The activity family hands its log over without two writers: the old
owner's recorder stops (its spans end, its session stops) before the new
owner's starts, and the new one hears the connections' states as they are
(`connection_status` signals stamped with the handover's time). While the
owners table gives the family to Rust and the core has not connected yet,
the front holds what it would record, with the time each came, until the
core takes the family (they go to it) or 15 s pass (Bun's recorder records
them). A browser's `activity.presence` reaches the core with the page's
`socket_id`; `bridge.activity.timeline` while Bun owns the family is a
shadow read of the log opened read-only.

The core runs on the real clock, but its families follow the front's test
clock: when the front runs on one, `welcome.clock` is its time, and after
each `advance` the front calls `internal.clock.advance {to}` (the test
clock's new time) and waits for its reply, which comes once the families'
timers due by then ran. A release core ignores `welcome.clock` and answers
`internal.clock.advance` with the error code `no_test_clock`.

### The host family

While the core owns the host family it is the one process with SSH
sessions and masters to the hosts, and connections.json's one writer: its
connection manager makes the generations browsers see, its profile service
answers `connections.list` and the profile changes, and each of its
runtimes owns the generation's tunnel and command master, the probe of the
Herdr sockets, and the Herdr control client with the event and agent status
subscriptions. The front keeps each generation's composition root
(conversation mode, the workspace, the terminal bridge, history watch, tab
titles): the core's runtime asks it to build it (`host.runtime_start`)
once the transport is up and before its subscriptions start, so a
connection is ready only once the front's part is, and disposes it
(`host.runtime_stop`). The front's part reaches Herdr through
`internal.host.herdr_call` and the host through `internal.host.run` and
`internal.host.ssh_hold`; the forwards of ports (`forward.*`, their own
connections, no slot) stay the front's until Phase 7.

The switch is one handover in each direction: when the table gives the
family to Rust and the core is connected, the front stops all its
connections (their masters and tunnels with them), then calls
`internal.host.start`; when it goes back (the table, or the core going),
the front calls `internal.host.stop`, disposes what is left of its parts,
ends the masters of a core that died with them up, reads connections.json
again and starts its own. A front whose table names Rust waits up to 10 s
at startup for the core to take the connections before starting its own.
At its shutdown the front calls `internal.host.stop` before the channel
goes.

## CLI pass-through

A family's `cli` entries in families.json are commands of `roamgate`, or a
command and its first word (`setup voice` is the voice family's while
`setup`'s other words stay with the command's own). When
the Bun CLI runs one of them and the owners table gives that family to
`rust`, it runs the core binary instead, with the same arguments
(`<core> <command> <args...>`): `ROAMGATE_CORE_BIN` when set, else the
table's `core` (the path of the binary that last wrote it with `roamgate
owners`). The child gets the CLI's environment plus `ROAMGATE_CLI_EXEC`,
`ROAMGATE_CLI_VERSION` and `ROAMGATE_CLI_STANDALONE`, its standard input,
and its output lines go to the CLI's own output (its standard output as
bytes, untouched, when the CLI writes to a real standard output: `archive
cat` prints a transcript byte for byte); the CLI exits with the
child's exit code. Without a core binary to run, the Bun CLI runs the
command itself and says so on stderr. The table is read once per command:
a CLI run needs no server.

## Owners table

`<data>/runtime/owners.json`, read by the front at start and whenever it
changes; the server never writes it. `roamgate owners` (a hidden command of
the Rust binary, temporary like the channel) shows it and is its one
writer: `roamgate owners set <family>... rust|bun` flips families,
`roamgate owners shadow on|off|<rate>` sets the shadow reads; it refuses
unknown families and a file it cannot parse, writes the file whole (0600,
by rename), and records its own path as `core` for the CLI pass-through.

```json
{
  "version": 1,
  "owners": { "limit_resume": "rust" },
  "shadow": { "enabled": true, "rate": 0.1 },
  "core": "/home/me/.local/share/roamgate/core/roamgate"
}
```

A family missing from `owners` is Bun's. A missing or invalid file means
every family is Bun's and shadow reads are on at rate 0.1 (an invalid file
is logged once per change). The families, the methods and paths of each, and
the files each writes are declared in `contract/owners/families.json`; a
method or path belongs to the family with its exact name, else to the one
with the longest matching prefix.

The update and herdr_setup families are routed at their own routes rather
than before them: the front keeps its method match and idle budget for
those paths, then hands the request to the core when the core serves the
family; their handlers check the confirmation headers themselves.

The front routes a browser RPC or an HTTP request to the core only when its
family is given to `rust`, the core is connected, and its `hello` named that
family; otherwise the front serves it. The `test` family routes only with
`ROAMGATE_CORE_TEST=1` on both sides.

## One writer per file

Each file of `contract/storage/index.json` is written by at most one family
(`files` in families.json; no file is in two families), and only the side
that owns that family writes it. The side that does not own a family neither
answers its methods (routing) nor runs its background writers: each side's
family code asks the owners table (`bunOwns(family)` in Bun,
`Owners::check_write` in Rust) before writing, and Rust's check refuses a
write of a family it does not own. SQLite databases may be opened read-only
by the non-owner for shadow reads (WAL). The session secret's rotation stays
with the auth owner, and both sides take the same mkdir lock.

## Shadow reads

For a method in its family's `shadow` list, the side that answered (the
owner) also sends the call to the other side, when that side has the family,
after the browser got its answer, and compares the two results. Writes are
never doubled.

- Sampled: each eligible call is shadowed with probability `shadow.rate`, at
  most once per method every 5 s, at most 2 at a time, only when the
  request's params and the owner's result are under 256 KiB of JSON each.
  A shadow call that takes more than 10 s is abandoned. A side that cannot
  answer a shadow read while it does not own something the read needs (the
  MR reviews' inbox while the review family is Bun's) declines it with the
  error code `shadow_declined`: no comparison, nothing logged.
- Paused while GameMode reports a game (`gamemoded -s`, asked at most every
  30 s; through `host-spawn` in a toolbox), and when `shadow.enabled` is
  false.
- The comparison (`shadowDiff` in the vectors) takes both results as JSON
  carries them to a browser (a key whose value is undefined in Bun's answer
  is absent, as on the wire) and walks them: an object
  by the owner's keys in order, then the other's extra keys; an array
  element by element after comparing lengths; it reports `missing`,
  `extra`, `type` (with both JSON types), `length` (with both lengths) and
  `value` (never the values themselves) at a path like `$.items[3].name`
  (`$["a-b"]` for a key that is not an identifier), and keeps the first 20.
- A difference is logged as one `[shadow]` warning line and appended to
  `<data>/runtime/shadow.jsonl` (`{at, method, family, owner, diffs,
  truncated}`), which is rotated to `shadow.jsonl.1` past 5 MiB. A shadow
  call that fails is logged the same way with `error`.
