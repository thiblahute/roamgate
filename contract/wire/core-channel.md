# Core channel

The server is two processes of the same binary: the **front**
(`roamgate [server flags]`), which holds the port, TLS, auth, the web
app's files and the browser sockets' framing, and the **core**
(`roamgate core`), a portless process the front spawns, which serves every
family. This file is the contract between them, the `roamgate-channel`
crate's (`crates/roamgate-channel`), held to
`contract/vectors/core-channel.json`.

## Variables

| Variable                   | Read by | Meaning                                                                                                                                                                                                                                |
| -------------------------- | ------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ROAMGATE_CORE_CHANNEL`    | core    | Where to connect: a Unix socket path, or a named pipe (`\\.\pipe\...`) on Windows. Set by the front for its child only.                                                                                                                |
| `ROAMGATE_CORE_TOKEN`      | core    | 64 hex digits the core proves itself with in `hello`. Set by the front for its child only.                                                                                                                                             |
| `ROAMGATE_CORE_SERVED_LOG` | core    | A debug core appends `<family> <what>` to this file for each browser call, HTTP request and CLI command of a family it served, `reverse-missing <target>` and `unported <what>`: the parity suite's report. A release core ignores it. |
| `ROAMGATE_CLI_EXEC`        | core    | The front's executable, which `update` and `rollback` replace. Set by the front on its core. Unset (a CLI run): the running executable.                                                                                                |
| `ROAMGATE_CLI_STANDALONE`  | core    | Set by the front on its core: `0` for a debug build (a checkout's, never replaced by an update), else `1`.                                                                                                                             |
| `ROAMGATE_CORE_TEST`       | core    | `1` turns on the `test.echo` family and reverse target used by the channel's own test. Honoured by a debug build only.                                                                                                                 |

The core gets the front's environment otherwise (HOME, data root, the
entries of `roamgate service run`'s environment file), with the
variables the front sets for it (The core, below).

## Process

- The front creates `<data>/runtime` (0700), listens, then spawns its own
  executable as `roamgate core` with `ROAMGATE_CORE_CHANNEL` and
  `ROAMGATE_CORE_TOKEN`. The spawner always listens and the child always
  connects, so neither waits on the other's readiness: the socket exists
  before the child starts.
- The socket is `<data>/runtime/core-<front pid>.sock`. When that path is
  longer than 100 bytes (Unix socket paths are limited to 104 to 108), it is
  `core.sock` in a fresh 0700 directory made with `mkdtemp` under the
  temporary directory. On Windows it is the named pipe
  `\\.\pipe\roamgate-core-<front pid>-<16 random hex digits>`. The front
  removes its own when it stops.
- The front logs `listening` as it welcomes the first core; a request that
  comes while no core is connected (starting, restarting) waits for one,
  30 s at most, then gets a 503.
- The core's stdout and stderr are the front's (its log lines land in the
  same journal), its stdin is closed.
- A core that does not say `hello` within 10 s, or goes 30 s without
  sending a frame while a ping has waited 20 s for its `pong`, is killed. A
  core that exits or is killed is spawned again after 1 s, doubling up to 5
  minutes, and the delay starts again at 1 s once a core has stayed up 10
  minutes. A `refused` core (wrong token or protocol) waits the same way,
  so a stale binary never spins. The browser sockets of a core that went
  are closed with 1012 `Service Restart`: their state was in it.
- The core exits when the channel closes (the front stopped or died): it
  never outlives its front.
- At its shutdown the front calls `internal.front.stop` (the connections
  stop, at most 10 s), then says `bye` and gives the core 15 s to finish
  (its stores flushed) before killing it.

## Frames

The voice helper's codec (`contract/vectors/voice-frames.json`): a
little-endian u32 length of what follows, a kind byte, the payload. The
channel accepts frames up to 64 MiB (length field, kind byte included).

| Kind | Payload                                                                                                                                                                                                                                                                                                                           |
| ---- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 0    | One message: a compact JSON object, UTF-8                                                                                                                                                                                                                                                                                         |
| 2    | A body chunk: the stream's u32 (little-endian), a flags byte, then the bytes. Flags: bit 0 `END` (last chunk), bit 1 `RESPONSE` (a response's body, not a request's)                                                                                                                                                              |
| 3    | A message with its `data` apart: the JSON's length (u32, little-endian), the message as kind 0 has it without `data`, then `data`'s UTF-8 bytes. Only to a front whose `welcome` has `raw_data`, and only for a `ws_send` of 4 KiB or more: escaping a large reply into the JSON and reading it back were two more passes over it |

Other kinds are an error that closes the channel. Body chunks carry at most
256 KiB of bytes each.

## Messages

Every message has `t`, its type. Requests (`call`, `reverse_call`, `http`)
carry an `id`: each side numbers its own requests from 1, and a `reply`,
`http_resp`, `cancel` or `ack` names the id of the request it is about, in
the numbering of the side that sent that request. A message of an unknown
`t` is ignored (logged once), so either side can add messages without the
other breaking.

| `t`            | From                | Fields                                                                                                                               | Meaning                                                                                                                                                                                                                                                                                |
| -------------- | ------------------- | ------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `hello`        | core, first         | `protocol` (1), `token`, `version`, `pid`, `families` (the families it implements), `test` (bool)                                    | The core introduces itself.                                                                                                                                                                                                                                                            |
| `welcome`      | front               | `protocol`, `clock` (optional), `raw_data` (optional)                                                                                | The token and protocol are right. `clock`: the front runs on the test clock (contract/wire/test-clock.md), whose time this is; see The core. `raw_data`: the front reads kind 3 frames.                                                                                                |
| `refused`      | front               | `reason`                                                                                                                             | Wrong token or protocol; the front closes the channel.                                                                                                                                                                                                                                 |
| `call`         | front               | `id`, `method`, `params`, `ctx`                                                                                                      | A call the core answers (the front's `internal.*` calls).                                                                                                                                                                                                                              |
| `reply`        | either              | `id`, then `result` or `error` (`{message, code?, data?}`)                                                                           | The answer to a `call` or `reverse_call`, or an `http` that failed before its `http_resp`.                                                                                                                                                                                             |
| `cancel`       | the requester       | `id`                                                                                                                                 | The browser socket or HTTP client is gone: the answer is no longer wanted. The other side may stop; it still sends nothing or a `reply` it already had.                                                                                                                                |
| `push`         | core                | `message`, `key` (optional), `connection_id` and `connection_generation` (optional), `socket_id` (optional), `session_id` (optional) | A push to browsers: `message` is the browser message. With `connection_id` the front sends it in that connection's envelope; `socket_id` limits it to one browser socket, `session_id` to one login's sockets. `key` is its coalescing key, on the channel and on each browser socket. |
| `http`         | front               | `id`, `method`, `url` (path and query), `headers` (`[[name, value]]`, names lowercase), `ctx`, `body` (bool)                         | An HTTP request the core serves; with `body`, chunks of stream `id` follow, the last with `END`.                                                                                                                                                                                       |
| `http_resp`    | core                | `id`, `status`, `headers`, `body` (bool)                                                                                             | Its response head; with `body`, chunks with `RESPONSE` follow, the last with `RESPONSE` and `END`.                                                                                                                                                                                     |
| `ack`          | the body's receiver | `id`, `response` (bool), `bytes`                                                                                                     | That many more bytes of the body were consumed.                                                                                                                                                                                                                                        |
| `reverse_call` | core                | `id`, `target`, `args`, `ctx` (optional)                                                                                             | A call into what the front does (`server.scheduleExit`, `voice.session_cookie`). Answered by `reply`.                                                                                                                                                                                  |
| `ping`, `pong` | either              | `n`                                                                                                                                  | Liveness: each side pings after 10 s without sending anything, and the other answers at once, so a core waiting on a long call still sends a frame at least every 10 s while the front keeps sending (and so never pings).                                                             |
| `bye`          | either              |                                                                                                                                      | The sender is stopping; the channel closes after it.                                                                                                                                                                                                                                   |

`ctx` is what the front knows of the request: `connection_id`,
`connection_generation`, `socket_id` (the front's number for the browser
socket), `lane`, `session_id` (the first 16 hex digits of the SHA-256 of
the login's session token, never the token itself), and for HTTP
`client_ip`. Fields that do not apply are left out.

A body's sender keeps at most 4 MiB of it unacknowledged; the receiver
acknowledges bytes as its consumer takes them, so a slow browser slows the
core rather than filling the front's memory.

The front terminates every browser WebSocket, and each becomes a **virtual
socket** in the core, driven by the messages of "Browser sockets" below.

## Browser sockets

What the front serves itself: `/health` and `/healthz`, the URL-token
login, `/login`, `POST /api/login`, `POST /api/login/pin`, `/api/logout`
(closing the browser sockets of that login with 4001 `Logged out`), the
login icon, the auth gate, the web app's files and manifest (a `GET` or
`HEAD` outside `/api/`, `/ws` and `/rendered/`, not cross-site), and the
`/ws` transport (flow control, coalescing, compression, chunking, the
acknowledgements, which never reach the core). Everything else is an `http`
to the core with the request as the browser sent it (cookie included) and
`ctx.client_ip`; the core runs its own routing on it.

| `t`          | From  | Fields                                                                              | Meaning                                                                                                                                                                                                                                                              |
| ------------ | ----- | ----------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ws_open`    | front | `id`, `socket_id`, `method`, `url`, `headers`, `ctx`                                | A browser asks to upgrade: the core runs its routing on the request. Answered by `reply`: `result` `{accepted: true, transport: "ws" \| "raw"}` (the core upgraded it), or `{accepted: false, status, headers, body}` (the response the browser gets, body as text). |
| `ws_message` | front | `socket_id`, `data` (text), `binary` (bool, `data` base64)                          | A message of an accepted socket (`/ws` acknowledgements excluded).                                                                                                                                                                                                   |
| `ws_close`   | front | `socket_id`, `code`, `reason`                                                       | The browser socket closed; the core runs its close handling once.                                                                                                                                                                                                    |
| `ws_send`    | core  | `socket_id`, `data` (text), `binary` (bool), `context` (optional), `key` (optional) | A message to the browser. On a `ws` socket it goes through the front's flow with `context` and `key`; on a `raw` socket it is sent as it is.                                                                                                                         |
| `ws_drop`    | core  | `socket_id`, `key`                                                                  | Forget a held message of that key (`dropCoalescedMessage`).                                                                                                                                                                                                          |
| `ws_end`     | core  | `socket_id`, `code` (optional), `reason` (optional)                                 | The core closes the browser socket.                                                                                                                                                                                                                                  |

`socket_id` is the front's number for the browser socket, as in `ctx`. A
`ws_send` before the `reply` to `ws_open` is held by the front until the
handshake is done. The core's virtual socket reports `readyState` 1 until
`ws_close` or its own `ws_end`, and a buffered amount of 0: back pressure,
the 8 and 64 MiB limits and the 30 s stall rule are the front's.

## The core

- The core serves every family of `families.json` it implements, from
  the `welcome` on. The `welcome` has `clock` when the front runs on a
  test clock; each `advance` of the front's clock is then relayed as
  `internal.clock.advance` (no `ROAMGATE_TEST_CLOCK` of its own: the front
  sets it empty). Every browser socket and every route the front does not
  serve itself go to the core on the channel.
- Before any browser request reaches it, the front calls
  `internal.front.start` with the server's configuration (`socket_path`,
  `client_socket_path`, `ssh_host`, `session`, `has_explicit_socket_path`,
  `has_explicit_client_socket_path`, `task_notification_source`,
  `auth_required`, `tls`: whether the front serves HTTPS, the scheme of the
  URLs it was reached on, `port`: the port it listens on, `generations`); the core starts its connections from it
  (the host family's `internal.host.start`) and answers at once. At its
  shutdown the front calls `internal.front.stop` (the connections stop,
  at most 10 s) before `bye`. On a test clock the front then sends one
  `internal.clock.advance` to its own time: an `advance` while the core
  was being welcomed and started had no core to reach.
- The front sets on its core what the server's configuration asks of the
  core's process: `ROAMGATE_PROFILE` `1` on its first start, with
  `ROAMGATE_PROFILE_DURATION` (seconds) and `ROAMGATE_PROFILE_DIR` (the
  directory the front resolved), when `--profile` or the environment ask
  for a CPU profile (the core samples itself and ends the capture on its
  families' clock), else `0`; and `ROAMGATE_CONTRACT_RECORD`, the record
  directory the front resolved (`0` when record mode is off): the front
  records the requests and browser sockets, the core the processes its
  runners start, in that directory. Variables of `roamgate service run`'s
  environment file reach the core as the front's own.
- The core's `front` family takes what no family declares: the `/ws`
  socket (the routing: the hello and the forwards registry on open, each
  RPC checked, routed to its connection and then to the family that
  declares its method, replies in the connection's envelope,
  `bridge.ping`, `bridge.status`, `bridge.pause_others`, and a
  connection's other methods passed through to its Herdr, topology lists
  as deltas), `/api/health`, and the connection-scoped routes
  (`/api/connections/<id>/...` and their legacy paths: `herdr-info` from
  the connection's Herdr, the file and agent-session routes from their
  families at their legacy paths, the connection in `ctx`; the uploads,
  staged per connection generation and swept while it runs), and the
  notification feed's socket `/api/notifications/ws` (its links on the
  origin the client reached, a ping answered at once by the front's link as
  it was for the feed). The browser RPCs of no family are answered with
  what the server adds over Herdr (overlays, agent
  activity and seen marks, worktree parents, git status, integration
  versions, `connections.agent_sessions` as changes from the version the
  socket holds, the agent profiles' settings, the forge chips and
  sessions, the port forwards with their registry's push and the hello's
  list), and the `terminal.*` RPCs and creation from a browser terminal
  (`tab.create`, `workspace.create` with `browser_source`, the
  empty-session bootstrap included) by the generation's terminal bridge
  (endpoint generation 1 sessions or the legacy direct client, streams
  shared by their viewers and kept warm, frames cropped to each viewer's
  size and sent with their coalescing keys, the popup observer, the
  clipboard relay of Herdr before protocol 22).
  A connection's endpoints that a family declares (`agent_sessions`'
  downloads, `workspace`'s file routes) reach the `front` family first
  when their `ctx` names no connection: it resolves the connection and
  hands them to the family with it.
- Reverse targets are answered in the core's own process, from a registry
  the binary fills; a target nobody registered fails with code
  `unknown_target`, its message naming it. A debug core notes each such
  failure in `ROAMGATE_CORE_SERVED_LOG` as `reverse-missing <target>`, and
  each refused method or route as `unported <what>`. The core answers each
  on its own families: the connections' (`connections.list`, `.ready`, `herdr.call`,
  `herdr.ping`, `herdr.setupGuard`, `host.run`, `workspace.ssh_run`,
  `activity.hostScript`, `agent_sessions.*`, `agent.transcript_tail`,
  `agents.addresses`; commands on an SSH host through the host family's
  session slots), conversation mode's and the Claude mods'
  (`conversation.host`, `.owned_panes`, `.prompt`, `claude_mod.*`; the
  Claude mod hub runs in the core from its start), `profiles.*`,
  `assistant.*` (a dispatch gate is the core's own closure, evaluated by
  its token), `settings.changed` and `settings.limit_resume.get`,
  `history.*`, `workspace.kept_steps`, and each
  generation's `host.runtime_start`, `.runtime_stop`, `.events`, `.status`
  and `.master_ready`, which feed the other families what each
  connection generation's runtime gives them (the workspace family's runtime and its events, conversation
  mode's `attach`, closed panes and sweeps, the activity log's signals,
  the usage limit resumer's pokes, the notifications a pane's events
  withdraw, Ranger's connection table, the claude start hook, and the
  review family's agents: `internal.review.agents` with this machine's
  socket key and each SSH connection's, on each status change and every
  second when changed), and each generation's composition: the terminal
  bridge, the task events (Herdr's semantic notifications on a passive
  endpoint shell, or Roamgate's own status tracker, labelled from Herdr
  and published to the feed, relayed to the pages as
  `roamgate.task_notification`), the tab auto-renamer; `.master_ready`
  sets an SSH host's review client up over the connection's master, its
  socket forwarded to the connection's agent socket.
  `server.scheduleExit` goes on to the front as the reverse call it is:
  the front answers `{scheduled: true}` and a second later stops as
  on a signal, with code 0.
  The review family's targets are answered there too: `review.socket`
  (the agent socket's host: the connections' checkouts and Last steps, the
  boards' tools, notifications, the agent messenger, conversation mode's
  holder, prepared launches, the Claude mod hub), `review.host` (git reads
  of a checkout on its host, a merge request's from its forge when the
  checkout lacks its commits, agent panes and sessions), `review.forge`,
  `review.connection` (with the rendered pages' tokens and their sites'
  storage) and `review.published`; the mr_reviews
  family's (`mr_reviews.connections` through `.agent_command`: the inbox's
  forge reads with this machine's glab and gh through the server's one
  forge gate, the reviews agent's turns on Claude Code), the work
  family's (`work.*`), the voice family's (`voice.errand_*`,
  `voice.work_*`), and the notification feed's (`notifications.feed`,
  `.clients` and `.current` with no feed socket held, `.clear_pane`);
  `mr_cache.load` has no reader to answer (the core's own readers read
  the cache in its process). `voice.session_cookie` goes on to the front,
  which answers `{cookie}`: a new login of its authentication, null when
  none is required.
- The `front` family also serves rendered reviews' pages,
  `/rendered/<token>/...` (the front sends them before its gate), and a
  sandboxed frame's request off its token (cross-site: a page saying so
  to a frame, 404 to anything else from an opaque origin).
- Pushes go to the `/ws` sockets the core holds, as `ws_send` with
  context `core-push` and the push's key, filtered by connection, socket
  and login, in the connection's envelope.

### Pushes and coalescing

Each side writes its messages through one outbound queue. A push with a
`key` replaces a push with the same key that is still queued (not yet
written): the older one is dropped and the newer one goes to the end of the
queue, so it never overtakes messages queued before it. A push already
written is never replaced. The front also passes the key to each browser
socket's send, which coalesces the same way there.

## Families in the core

The core serves the families its binary implements (`hello.families`); a
browser call goes to the family whose `rpc` entries name its method, an
HTTP request to the one whose `http` entries name its path
(contract/wire/families.json: an exact name, else the longest matching
prefix); what no family declares is the `front` family's. A family's code
runs its background work (timers, watchers) and writes its files only
while it serves: the core starts each family at the `welcome`, in order,
and stops it when the channel closes.

The front's own calls to a family are `call`s of `internal.<family>.<op>`
(no family declares the `internal.` prefix, so a browser never reaches
one): one family tells another something happened (a Herdr event, a
setting changed). Each family documents its
internal calls and its reverse targets with its code.

## One writer per file

Each file of `contract/storage/index.json` is written by at most one family
(`files` in families.json; no file is in two families), and only by that
family's code while it serves. The session secret's rotation stays with the
front, which takes the same mkdir lock as any other writer of the data
root.
